# API Contract - Notification Service

Base path: `/notifications`

All responses are `application/json`. Errors follow the shape:
```json
{ "error": "human-readable message" }
```

All endpoints require `Authorization: Bearer <access_token>`.

The Notification Service is **purely reactive** - it never initiates actions on its own; every side effect is triggered by a consumed RabbitMQ event. It consumes events, exposes HTTP endpoints for clients to read/mark notifications, and sends transactional **email** (via SMTP) for the few events that warrant an out-of-band confirmation (see [Email delivery](#email-delivery)).

> **ID policy:** all IDs are Snowflake `BIGINT`s generated by the service. On the JSON wire they appear as quoted strings (e.g. `"123456789012345678"`) so JS clients can hold them without precision loss.

## REST Endpoints

### GET /notifications

Fetch notifications for the authenticated user. Dismissed notifications are excluded by default - they have been removed from the panel and are not meant to come back unless explicitly requested.

**Query params:**
| Param | Type | Description |
|-------|------|-------------|
| `read` | bool | Filter by read status. `false` = unread only. Omit for all. |
| `include_dismissed` | bool | If `true`, also return notifications the user has dismissed. Default `false`. |
| `limit` | int | Max results (default 50, max 100) |
| `before` | snowflake | Cursor for pagination |

**Response `200`:**
```json
[
  {
    "id": "<snowflake>",
    "user_id": "<snowflake>",
    "type": "mention",
    "actor_id": "<snowflake>",
    "source_id": "<snowflake>",
    "payload": {
      "channel_id": "<snowflake>",
      "guild_id": "<snowflake>",
      "preview": "T'es mauvais @yandry"
    },
    "read": false,
    "dismissed_at": null,
    "created_at": "2026-03-09T12:00:00Z"
  }
]
```

`dismissed_at` is `null` for active notifications and an ISO 8601 timestamp once the user dismisses them (see `DELETE /notifications/{id}`).

`actor_id` and `source_id` are top-level fields backed by dedicated columns (see `docs/schema/notification.sql`):
- `actor_id`: the user who caused this notification. Used for blocked-user suppression: before inserting a notification with a non-NULL `actor_id`, the service calls User Service `GET /internal/users/{target_user_id}/relationship-with/{actor_id}` and drops the notification if the relationship is `blocked_by_me` (i.e. the recipient has blocked the actor). NULL for system events, where no suppression is applied.
- `source_id`: the entity this notification deep-links to (a message, friendship, guild, etc.). NULL when there is no persistent target.

**Notification types - what each field carries:**

| `type` | `actor_id` | `source_id` | `payload` |
|--------|------------|-------------|-----------|
| `mention` | `author_id` of the message | `message_id` | `{ channel_id, guild_id, preview }` |
| `dm` | `sender_id` | `message_id` | `{ conversation_id, preview }` |
| `friend_request` | `requester_id` | friendship row id | `{}` |
| `friend_accept` | `addressee_id` (who accepted) | friendship row id | `{}` |
| `guild_invite` | `invited_by_user_id` | `guild_id` | `{ guild_name }` |
| `guild_welcome` | NULL (system event) | `guild_id` | `{ guild_name }` |
| `incoming_call` | `caller_id` | NULL (call is ephemeral) | `{ call_type: "audio" \| "video" }` |

### PATCH /notifications/{id}/read

Mark a single notification as read.

**Request body:** None

**Response `200`:**
```json
{
  "id": "<snowflake>",
  "read": true
}
```

**Errors:**
| Status | Reason |
|--------|--------|
| 403 | Notification does not belong to this user |
| 404 | Notification not found |

---

### GET /notifications/unread-count

Fast badge counter for the authenticated user. Returns just the count without paginating the full list. Used by the navbar bell on every page load.

**Auth required:** Yes (`Authorization: Bearer <access_token>`)

**Response `200`:**
```json
{
  "count": 7
}
```

`count` excludes dismissed notifications (`dismissed_at IS NOT NULL`) and read notifications (`read_at IS NOT NULL`). Backed by a partial index on `notifications (user_id) WHERE read_at IS NULL AND dismissed_at IS NULL` so the query stays O(rows-the-user-has-unread), not O(rows-the-user-has-total).

The count is also kept fresh in real time by the SSE stream (see below): a pushed notification bumps it and the client decrements it on read/dismiss, so most navbar updates happen without polling this endpoint; it is used on initial load and as a reconciliation fallback.

---

### PATCH /notifications/read-all

Mark all notifications as read for the authenticated user.

**Request body:** None

**Response `200`:**
```json
{
  "updated": 12
}
```

---

### DELETE /notifications/{id}

Dismiss a notification. Soft-delete: the row stays in DB with `dismissed_at` set so it does not reappear in the panel, but `include_dismissed=true` on `GET /notifications` can still surface it.

Dismissing also marks the notification as read in the same write (`read_at` is set if it was still `NULL`): removing it from the panel is treated as having seen it, so a dismissed row never lingers in an unread state.

**Response `204`:** No content.

**Errors:**
| Status | Reason |
|--------|--------|
| 403 | Notification does not belong to this user |
| 404 | Notification not found |

## Real-time delivery - Server-Sent Events (SSE)

Real-time alerts are pushed over a long-lived **Server-Sent Events** stream that the client opens with an `EventSource`.

### GET /notifications/events

An authenticated SSE stream (`Content-Type: text/event-stream`). While the stream is open, every notification created for the user is pushed immediately as a **named** SSE event (`event: ReceiveNotification`) whose `data:` line is a single JSON object:

```json
{
  "id": "<snowflake>",
  "type": "mention",
  "actor_id": "<snowflake>",
  "source_id": "<snowflake>",
  "payload": { "channel_id": "<snowflake>", "guild_id": "<snowflake>", "preview": "..." },
  "read": false,
  "created_at": "2026-03-09T12:00:00Z"
}
```

`actor_id` and `source_id` are nullable. The shape mirrors one element of the `GET /notifications` response (minus `user_id`, which is implicit from the connection). Because the event is named, clients subscribe with `EventSource.addEventListener('ReceiveNotification', ...)`, not the default `message` handler. The stream also emits a `: ping` comment heartbeat every 15s so idle connections survive proxy read timeouts.

The notification row is always persisted **before** the push, so a notification missed while the stream is closed (or dropped for a slow client) is never lost: it is recovered on (re)connect via `GET /notifications?read=false`. There is no `Last-Event-ID` replay, so clients should reconcile with that fetch each time the stream (re)opens.

> **Auth over EventSource:** browsers cannot attach an `Authorization` header to an `EventSource`, so the access token is passed as a query parameter: `GET /notifications/events?access_token=<jwt>`.

## Preferences Endpoints

Per-user mute settings for guilds and channels. Backed by `notification_preferences` (`docs/schema/notification.sql`). Before inserting a notification, the Notification Service checks whether the target user has a matching unexpired mute and skips the insert if so.

`scope_type` must be one of `guild` or `channel`. `scope_id` is the snowflake of the guild or channel.

### GET /notifications/preferences

List all preferences the caller has set. Defaults (no row) are not included - omission means "not muted".

**Response `200`:**
```json
[
  {
    "scope_type": "guild",
    "scope_id": "<snowflake>",
    "muted": true,
    "muted_until": "2026-03-10T00:00:00Z"
  }
]
```

`muted_until` is `null` for indefinite mutes.

---

### PUT /notifications/preferences/{scope_type}/{scope_id}

Create or update a preference for one scope.

**Request body:**
```json
{
  "muted": true,
  "muted_until": "2026-03-10T00:00:00Z"
}
```

`muted_until` is optional; omit (or `null`) for an indefinite mute. Setting `muted: false` keeps the row but disables muting - useful if a future default changes.

**Response `200`:** Updated preference object (same shape as the GET list entry).

**Errors:**
| Status | Reason |
|--------|--------|
| 400 | Invalid `scope_type`, or `muted_until` in the past |

---

### DELETE /notifications/preferences/{scope_type}/{scope_id}

Remove the preference, reverting the scope to default behavior (unmuted).

**Response `204`:** No content.

**Errors:**
| Status | Reason |
|--------|--------|
| 404 | No preference set for this scope |

## Internal Endpoints

Reachable only over the docker network. The API Gateway forwards `/api/{service}/vN/...`; `/internal/...` has no version segment and is not routed. No `Authorization` header required.

### GET /internal/users/{user_id}/data-export

The user's Notification-owned data for a GDPR self-serve export. Called by the User Service's public data-export aggregator, which fans out to every service and stitches the results into one bundle.

**Auth required:** None. Not reachable through the API Gateway. Callers reach this directly over the docker network (e.g. `http://notification:8080/internal/users/{user_id}/data-export`).

**Response `200`:**
```json
{
  "user_id": "123",
  "notification_preferences": [
    { "scope_type": "guild", "scope_id": "456", "muted": true, "muted_until": null },
    { "scope_type": "channel", "scope_id": "789", "muted": false, "muted_until": "2026-07-10T00:00:00Z" }
  ]
}
```

This is the internal-perspective twin of `GET /notifications/preferences`: every mute preference the user has set (`muted: true` and `muted: false` rows alike, since both are user-configured), with `muted_until: null` for indefinite mutes.

**Scope.** Deliberately limited to `notification_preferences` - the only data the Notification Service originates. The **`notifications` table is intentionally excluded**: its rows are a fan-in of other services' events (a `mention`/`dm` `preview` is a copy of another user's message, `actor_id` is a third party) and are already exported authoritatively by Chat, User, and Guild. Re-exporting them here would duplicate those legs and drag third-party content into the bundle, which GDPR Art. 15(4) weighs against.

`scope_id` is returned **raw**, not resolved to a guild/channel name: those names are owned by Guild, and resolving them would require a synchronous Guild call inside this export leg. The Guild leg of the same bundle carries the intelligible names; if fuller cross-referencing is wanted, the User aggregator is the place to resolve them during stitching. An unknown user, or one with no preferences, returns `200` with an empty array (a GDPR export, not a lookup).

**Errors:**
| Status | Reason |
|--------|--------|
| 400 | `user_id` is not a positive snowflake |

## RabbitMQ Events Consumed

| Event | Trigger | Notification created |
|-------|---------|---------------------|
| `chat.message_sent` | User is in `mentions[]` | `type: mention` for each mentioned user |
| `chat.dm_sent` | Always | `type: dm` for `recipient_id` |
| `call.incoming` | Always | `type: incoming_call` for `callee_id` - prompts them to open the app |
| `friend.request_sent` | Always | `type: friend_request` for `addressee_id` |
| `friend.accepted` | Always | `type: friend_accept` for `requester_id` - tells them their request was accepted |
| `friend.removed` | Always | no stored notification; pushes a transient `friends_changed` SSE signal to both `requester_id` and `addressee_id` so their friends lists re-fetch |
| `guild.invite_created` | `invited_user_id` is present | `type: guild_invite` for `invited_user_id` |
| `guild.member_joined` | Always | `type: guild_welcome` for the joining user |
| `user.deleted` | Always | Delete every notification row where `user_id` or `actor_id` matches the deleted user, and drop the user's `notification_preferences` rows. Also sends the `account_deleted` confirmation email (see [Email delivery](#email-delivery)). |
| `data.export_ready` | Always | No in-app notification row. Sends the `data_export_ready` email carrying the presigned `download_url` (see [Email delivery](#email-delivery)). |

## Email delivery

The Notification Service is the system's single outbound email channel. It runs an SMTP client configured by environment (host, port, from-address); the eval environment points it at a **MailHog** container, production at a real SMTP provider. Two events trigger a transactional email:

| Template | Trigger event | Contents |
|----------|---------------|----------|
| `account_deleted` | `user.deleted` | Confirms the account and its data were deleted. |
| `data_export_ready` | `data.export_ready` | "Your data export is ready", with the presigned `download_url` and its `expires_at`. |

Templates (plaintext + minimal HTML) are authored in #245. The service holds **no object-storage credentials**: it emails the presigned `download_url` from the event verbatim and never touches MinIO.

**Recipient address.** Emails need a real address, which the **Auth Service owns** (`users_auth.email`), not this service. The address therefore travels in the triggering event rather than being looked up:

- `user.deleted` must carry it (`{ user_id, email }`): by the time Notification consumes the event the Auth account is already deleted, so no lookup is possible.
- `data.export_ready` carries it for the same single code path; the aggregator already holds the address from Auth's export leg during fan-out.

OAuth-only accounts with no stored email address have nothing to send to and are skipped.
